# 快速失败错误策略（不重试）

LLM 与搜索调用不做重试。任何来自这些调用的错误都会被捕获到全局 state 的 `last_error` 与 `failed_step` 字段中；graph 转入 `failed` 终态，API 返回 4xx / 5xx 给前端。HITL Interrupt 不设超时——thread 一直暂停直到用户恢复。

## 备选方案

- **快速失败（已选）**：立刻把真实失败呈现给用户，代码路径线性、可推理，不存在隐藏的重试预算意外。
- **重试 + 超时 + 优雅降级**：生产 agent 的标准做法，但会在重试预算下掩盖瞬态失败，并让成本难以预测。
- **仅重试、不快速失败**：尽力而为的健壮性，但卡住的调用仍可能在静默中耗尽 recursion limit。

## 影响

- 每个错误都有唯一的责任方：失败的那次调用，并暴露给用户。不存在“这是不是第 3 次重试才成功”的歧义。
- 用户必须显式恢复被 Interrupt 暂停的 thread；废弃的 thread 累积在 Redis 中直到 TTL 过期。
- 后续切到重试策略是工具层（LLM / search）的小幅封装改动，不需要触碰 graph。
